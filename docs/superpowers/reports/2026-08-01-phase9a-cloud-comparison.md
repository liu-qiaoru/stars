## 数据边界与执行过程

用户明确授权本次将私人素材的缩放抽帧、查询和时间戳发送给智谱与阿里云，费用上限 2 元。
程序没有上传完整视频、本地路径、Caption、转录、PostgreSQL 行或 Qdrant 向量。

执行顺序如下：

1. Python 只读 PostgreSQL 中 Phase 8 的冻结 run，校验原 12 条 candidate、人工等级、
   当前文件 generation 和场景边界。
2. FFmpeg 只读每个源视频，为场景生成最多 12 张、宽 640 像素的临时 JPEG；sampling
   fingerprint 与本地 Phase 9A 完全相同，均为
   `sha256:1fdc2a706b11a85d6641942bc735617983d989c09b2ccb9bfc018df1c8857c84`。
3. Python 同步调用云 API；每个模型看到相同图片、查询、时间戳和
   `frame-verify-cloud-v1` Prompt。同步表示当前请求返回后才处理下一次，没有并发洪峰。
4. 云端 `json_object` 只保证返回有效 JSON，不强制数组元素类型。因此统一 Prompt 明确
   写入四字段 Schema，客户端仍拒绝额外字段、错误类型、空字符串或非法等级。
5. 每个 Qwen 模型对每个场景重复 3 次。报告保存等级、理由、耗时、token 与估算费用，
   不保存图片、源路径或 API Key；所有临时帧在结束后删除。

这条链路没有创建 Server API 或 Worker 异步 Job，没有写 PostgreSQL/Qdrant，也没有改变
生产 RRF。无需数据库迁移、回填或重新索引。

## 人工理由复核

事实：Plus 的至少 3 个场景理由存在不受画面支持的动作或环境断言；Flash 至少 5 个。
两个模型都没有修复“只看到物体与姿态，就断言动作已经发生”的主要问题。

Plus 展现出两个有价值但不足以上线的特点：它把打字机与电脑区分开，并正确拒绝了室内的
“户外拿拍摄设备”候选。Flash 虽然速度快、费用低、等级重复稳定，但把打字机当电脑，且
在 `visual-outdoor-camera-30s-zero` 三次都出现等级与理由逻辑冲突。稳定输出错误 JSON 等级
比偶发超时更危险，因为它会稳定地把错误候选提升到前面。

## GLM 可用性结论

第一次完整尝试中，GLM 返回有效 JSON，但 `matched_constraints` 不是非空字符串数组；程序
按严格契约停止。增加统一云端 Schema 后，单例可以成功解析，说明格式根因已经修复。

随后正式运行的第 1 次 GLM 调用成功，第 2 次在距离前一次请求起点至少 30 秒后仍返回
HTTP 429。官方说明限额取决于账户权益、模型和平台负载，可通过控制台查看实际额度；本次
没有依据可证明 60 秒或更长固定间隔一定成功。因此 GLM 状态是“当前账户/时段无法完成
可复现评测”，不是“质量通过”或“质量失败”。

## 最终建议

事实：Flash 与本地 Qwen2.5-VL 都是 7/12，Plus 是 6/12；排除歧义标签后两个云模型均为
6/10。人工理由复核也没有通过。

推断：更大的云模型并没有自动解决本评测最难的关系、动作和环境约束问题。Plus 在物体类型
和环境冲突上更谨慎，但其等级不稳定；Flash 的速度与费用优势不能抵消逻辑矛盾。

建议：不要实施 Phase 9B，不把任何一个云模型接入生产多帧重排，也不为了得到更好数字而
放宽标签或解析规则。Phase 8 核心检索仍是当前可交付主线。若未来继续研究，应该先补约
20 条未见盲测样本并纠正两条歧义标签，再测试“逐约束二分类/打分”方案；不应继续在这
12 条已反复观察的样本上调 Prompt，否则会过拟合。过拟合是方案只适应当前小样本、换一批
真实素材就失效。
